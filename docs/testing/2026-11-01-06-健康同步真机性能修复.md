# 健康同步真机性能修复

- 日期：2026-11-01（Asia/Shanghai）；分支 `main`。
- 环境：Android API 36 真机与 API 36 Google APIs 模拟器。
- 真机包：`app.scalemate`，固定发布签名；诊断阶段使用同版本、同签名的临时可调试构建，结束后恢复不可调试发布构建。

## 问题与定位

用户在健康页观察到同步约一分钟。真机只读检查显示本地 `health_records` 约 4.8 万行，Health Connect 自身约 6.4 万条心率原始记录；复现的增量包含 1,737 条心率更新、71 条删除和两页变更日志。

第一次分段计时表明：

| 阶段 | 观测 |
| --- | ---: |
| Health Connect 变更日志 | 约 1.1 秒 |
| 受影响日期逐条 SQLite 查询 | 超过 70 秒仍未结束 |

根因不是健康平台读取慢，而是 `HealthStore.affectedDates()` 对每条 upsert／delete 分别执行 SQLite 查询并解析完整 JSON。事务中的 `applyIncremental()` 还会再次计算同一批日期。

批量修复后，同一路径的变更读取约 0.85 秒、删除记录查询约 0.16 秒、受影响日期约 1.4 秒、提交约 0.84 秒。

## 修复

1. 先把 upsert／delete 自身覆盖的日期加入集合，再按健康类别将 `recordId` 和 `platformId` 每 400 个批量查询。
2. 查询只读取 `start`、`end` 两列，不再逐行解析完整健康记录 JSON；跨日记录仍按本地时区展开。
3. `HealthSync` 把第一次计算出的受影响日期传给同一事务内的 `applyIncremental()`，不再重复查询。
4. `HealthSync` 增加可选分段计时和变更页数；默认关闭，显式设置 `log.tag.ScaleMateHealth=DEBUG` 时才采集。日志不输出健康值、平台 ID 或凭据。
5. 健康 AI 关闭时关闭 21 天基线读取。AI 开启时仍使用原来的 21 天参考基线；完整本地缓存不会被删除。

第二轮真机计时仍发现完整快照约 32 秒，其中本地记录读取约 19.7 秒、指标计算约 8.8 秒。主要原因是 `HEALTH_AI_ENABLED=false` 时仍加载未被展示路径使用的 21 天基线，因此增加 `baselineDays=0` 的生产配置。
