# 饮食图片识别失败复现与修复

> 2026-10-22。基于 `main` 当前实现排查照片／相册识别失败率偏高的问题。真实服务验证使用仓库外的私有配置；本文不记录密钥、图片内容、模型完整回复或用户健康／饮食数据。

## 当前原因

| 现象 | 代码位置 | 判断 |
| --- | --- | --- |
| 完整模型响应必须在 45 秒内返回 | `AiClient.kt` 的 `readTimeout=45000` 与普通非流式请求 | 长输出实测 36.6 秒，距离超时余量很小；弱网或多图更易超时 |
| 图片体积与请求体不是同一限制 | `FoodImages.kt`、`AiClient.kt` | JPEG 文件以 Base64 放入 JSON，编码后约增加 1/3；旧规则允许 6×4 MB 原图，极端请求体约 32 MB |
| 实况照片带 MP4 尾部 | `FoodImages.import` | 实测 `MVIMG_*.jpg` 含 `MotionPhoto` 与 `ftypmp42` 视频尾部；整份文件交给解码器会增加不必要的读取和内存压力 |
| 多种失败都显示“AI 没有返回可用的食物数据” | `AiClient.kt`、`FoodViewModel.kt` | 响应截断、非 JSON、合同缺字段、响应过大和未预期异常部分被统一映射，难以区分 |
| Live／实时接口 | 当前主分支 | 没有 Live API 或视频帧上传；相册实况照片的静态主图才是当前路径 |

## 本轮真实复现

使用私有 OpenAI 兼容测试服务与同一盘饭照片，不改动业务数据：

| 场景 | 请求体 | 结果 |
| --- | --- | --- |
| 旧尺寸 1600 px、质量 85 | 约 189 KB JPEG／约 252 KB Base64 | 单图可成功，但同一提示实测 5.4 秒 |
| 新尺寸 1280 px、质量 75 | 约 82 KB JPEG／约 109 KB Base64 | 同一提示实测 2.2 秒，返回 `finish_reason=stop` |
| 2 张新尺寸图片 | 约 219 KB JSON | 成功，约 4.1 秒 |
| 6 张新尺寸图片 | 约 655 KB JSON | 成功，约 3.2 秒 |
| 故意要求长回答 | 约 253 KB JSON | 36.6 秒完成，说明 45 秒余量不足 |
| 实况照片 `MVIMG_*.jpg` 转为静态 JPEG | 1600 px 约 124 KB | 成功，约 3.9 秒；说明失败并非所有实况照片必然不可识别 |

以上结果只证明当前测试服务和网络下的表现，不承诺其他供应商、模型或用户网络同样速度。

## 已实施

- 新导入图片最长边改为 1280 px、JPEG 质量 75，单图上限 1.5 MB；6 张原始 JPEG 总预算 8 MB，Base64 后仍低于 11 MB。
- 图片识别读取超时改为 120 秒，连接超时 20 秒；纯文本连接测试仍使用 45 秒。
- 响应超过 1 MB 单独提示“返回内容过大”，未预期请求异常不再伪装成“AI 没有返回可用的食物数据”。
- 保留 `calculationMode: personal` 合同与客户端不二次分摊的规则。

## 验证与边界

- `FoodImageBudgetTest` 验证 Base64 预算、6 张上限、识别超时下限，并锁定旧 6×4 MB 规则会形成至少约 32 MB 的 Base64 请求；这是确定性的失败边界复现，不需要提交真实照片或消耗模型额度。
- JVM 单测、Lint、普通 Debug 构建通过；构建仍保留既有 Compose／Android API 弃用告警。
- 本轮开始时 `adb devices -l` 为空，未完成手机实机重拍／相册实况照片导入验证；不能把本地解码分析和公开服务请求当作实机通过。
- 动态照片的静态主图处理依赖 Android `ImageDecoder` 对选择器 URI 的解码行为；拿到设备后应分别验证相册实况照片、普通 HEIC／JPEG 与拍照三条路径。
