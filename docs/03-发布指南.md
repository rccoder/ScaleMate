# 签名与 GitHub 发布

## 固定发布签名

发布密钥只生成一次，后续 APK 持续使用同一密钥签名。当前本地文件位于仓库外：

- `~/.local/share/scalemate-signing/scalemate-release.jks`：私钥库。
- `~/.local/share/scalemate-signing/credentials.json`：密钥库密码、密钥密码与别名。

目录权限 0700，文件权限 0600。请将这两个文件备份到加密存储或密码管理器；不要放进 Git 仓库，也不要在聊天或 CI 日志里输出内容。GitHub Secrets 是发布用副本，不代替自己的备份。

本地构建：准备 JDK 17 与 Android SDK 后运行 `python3 scripts/signing.py build`。密钥信息通过环境变量传给 Gradle，不写入项目配置。缺少完整签名配置时，release 打包会失败，避免发布未签名 APK。

## GitHub Secrets

完成 `gh auth login` 后，运行：

```sh
python3 scripts/signing.py upload-secrets
```

脚本通过标准输入设置以下仓库 Actions Secrets，不在命令参数或输出里包含秘密：

- `ANDROID_KEYSTORE_BASE64`
- `ANDROID_KEYSTORE_PASSWORD`
- `ANDROID_KEY_ALIAS`
- `ANDROID_KEY_PASSWORD`

设置位置：仓库 Settings → Secrets and variables → Actions。Base64 只是二进制编码，保密由 Secrets 提供。公众看不到；能修改并执行发布工作流的人可能获取秘密，因此发布工作流的修改权限也应由可信维护者掌握。

## CI 与发布

`.github/workflows/ci.yml` 在 main 提交、PR 或手动触发时检查翻译、运行 JVM 单元测试、Android Lint 并构建 debug APK，不读取签名密钥。Android 仪器测试可在 API 36 AVD 运行；发布前的实秤、Health Connect 目标应用读取和覆盖升级仍须实机完成。

`.github/workflows/release.yml` 在推送 `vX.Y.Z` 或 `vX.Y.Z-preview.N` 标签时检查版本号、测试与 Lint，再读取 Secrets 构建签名 release APK。密钥只在签名步骤恢复到 runner 临时目录，退出步骤时删除；签名任务不写入 Gradle 缓存。验证 APK 签名与 `gradle/release-certificate.sha256` 中的固定公开证书指纹一致，并确认非调试属性后，生成并使用同一固定发布密钥签名 `update.json`，附带 `update.json.sig`；同时生成 `releases.json`／签名供审计。APK、摘要、公开证书和四份元数据一起上传 GitHub Releases。客户端通过 Releases API 发现候选，以每个 Tag 的签名清单验证版本与文件。预览 Tag 创建 prerelease，正式版创建普通 Release。

## 双通道发布操作

本节是后续 Agent 的执行入口；[根目录协作指南](../AGENTS.md#双通道发版与升级验收) 要求发布前阅读。两种版本都走 `.github/workflows/release.yml`，不创建不同包名或独立预览签名。

调试用测试版运行完整称伴，构建参数沿用 `-PfoodDev`、包名沿用 `app.scalemate.fooddev`，显示为“称伴 · 测试版”、橙色图标；它不进入公开更新通道。公开发布不带隔离测试参数。临时仪器测试工具不作为第四种产品版本或用户安装包发布。

| 项目 | 预览版 | 正式版 |
| --- | --- | --- |
| 版本名／Tag | `X.Y.Z-preview.N`／`vX.Y.Z-preview.N` | `X.Y.Z`／`vX.Y.Z` |
| GitHub Release | prerelease，不能占 Latest | 普通 Release，可成为 Latest |
| versionCode | 大于两个通道历史最大值 | 大于两个通道历史最大值，包括刚验证的预览版 |
| 更新说明 | 本版变化、具体已知问题、不稳定风险、安装与费用限制 | 已实现变化、升级／权限／费用限制，不声称预览数据另行合并 |
| 发布前门槛 | 本地校验、同一提交 Android CI 成功 | 相关预览验收通过、本地校验、正式发布提交自身 CI 成功 |
| 发布后门槛 | 实际附件核验、应用内升级、失败／取消与数据保留验证 | 重新核验实际正式附件、预览→正式应用内覆盖升级验证 |

### 发预览版

1. 检查当前版本、已有 Tag 与两个通道的 Release，分配新的全局版本码；不要照抄历史测试版本码。
2. 修改 `app/build.gradle.kts` 为 `X.Y.Z-preview.N`，新增 `docs/releases/vX.Y.Z-preview.N.md`。预览发布时 README 的正式下载入口仍指向最新正式版，不能让 `/releases/latest` 指向预览。
3. 执行标准流程的本地检查，提交并推送 main；等该 SHA 的 `ci.yml` 成功。
4. 在已通过的同一提交创建并推送 annotated Tag：

```sh
python3 scripts/check_release.py --tag vX.Y.Z-preview.N --check-previous-code
git tag -a vX.Y.Z-preview.N -m 'ScaleMate X.Y.Z-preview.N'
git push origin vX.Y.Z-preview.N
```

5. 等 Tag 对应 `release.yml` 成功；`gh release view <Tag> --json isPrerelease,tagName,assets` 必须显示 prerelease，且七个附件齐全。
6. 下载真实 Release 附件，按后文验证 SHA-256、固定签名、包名、版本名／码、非调试属性、清单签名和元数据一致性；至少验证实际代理下载。
7. 在保留数据的手机上，先确认正式通道看不到该预览，再主动选择预览通道，完成发现、选线、下载、校验、Android 授权／安装、重启和数据保留检查。系统拒绝或用户取消后能重试，禁止卸载、清数据或降低版本码。

### 验证后转正式版

1. 只有预览验收通过才继续；发现缺陷先修复并发更高版本码的下一预览，不修改已经公开的 Tag 或附件。
2. 将版本名改为 `X.Y.Z`，versionCode 分配为比该预览和全部历史发布都更大的值，添加 `docs/releases/vX.Y.Z.md`，更新 README 正式版本说明。
3. 重新执行本地门槛，提交并推送；等待**正式发布提交自己的 CI**，不能借用预览提交的绿色状态。
4. 在该提交创建并推送正式 annotated Tag：

```sh
python3 scripts/check_release.py --tag vX.Y.Z --check-previous-code
git tag -a vX.Y.Z -m 'ScaleMate X.Y.Z'
git push origin vX.Y.Z
```

5. 等发布成功，确认 `isPrerelease=false`、七个附件齐全、Latest 指向正式版；重新下载这些实际附件并完整核验。
6. 已安装预览版的手机在预览通道也应发现更高正式版，完成应用内下载与系统覆盖安装；验证记录、草稿、设备、AI 服务和默认项保留，旧更新红点清除。最后恢复用户原本通道及线路偏好，清理本轮私有测试夹具。
7. 将结果写入验收记录并提交推送。发布完成必须同时有云端附件和升级证据，不能只报告工作流成功。

### 只读数据保留检查（可选加强验收）

`UpdateUpgradeDataTest` 仅在显式 `upgradeSnapshotMode=capture/verify/cleanup` 且目标包为 `app.scalemate` 时执行；仅只读打开原数据库，在应用私有目录保存摘要，不输出任何记录、API 配置或密钥。先 capture 一次，预览／正式升级后分别 verify，全部结束后 cleanup。

对非调试正式包执行仪器测试时，测试 APK 必须以同一固定发布证书签名、instrumentation 的目标包必须为 `app.scalemate`；不能安装 debug 正式包来取得访问权限，也不能用 `foodDev` 的隔离数据库冒充用户数据保留。

```sh
adb -s <serial> shell am instrument -w \
  -e class app.scalemate.UpdateUpgradeDataTest \
  -e upgradeSnapshotMode capture \
  app.scalemate.test/androidx.test.runner.AndroidJUnitRunner
```

后续将 `capture` 换为 `verify`、最后 `cleanup`。普通测试运行会跳过该测试，不能把跳过算作数据保留通过。只读摘要比较不代替应用内下载与系统安装路径的验证。

## 每次发布的标准流程

正式版版本号使用 `X.Y.Z`，预览版使用 `X.Y.Z-preview.N`。根据改动决定版本：修复递增补丁号，新增完整能力可递增次版本；两者都使用 `app.scalemate` 和固定发布签名；`versionCode` 必须大于两个通道所有已发布版本的最大值。转正也要分配更高版本码，不能复用预览版本码。不要照抄历史文档中的版本号。

1. 完成相关功能验收与截图，按 [测试与验收指南](02-测试与验收指南.md) 记录结果和限制。检查工作区与待提交文件，不包含私有健康数据、密钥或测试安装包。
2. 更新 `app/build.gradle.kts` 中的 `versionName`、`versionCode`，添加与版本同名的非空 `docs/releases/vX.Y.Z.md` 或 `vX.Y.Z-preview.N.md`。预览说明必须写出已知问题及不稳定风险。更新说明覆盖用户能体验到的变化、安装升级限制、权限或费用边界；不把规划写成已实现。同步修正 README 中过时的版本提示。
3. 先同步完整公开 Tag 历史（浅克隆先 `git fetch --unshallow --tags origin`，完整克隆执行 `git fetch origin --tags`），本地运行 `python3 scripts/check_release.py --check-previous-code` 和 `python3 -m unittest discover -s scripts -p 'test_*.py'`；正常执行翻译、JVM 测试、Lint 与构建。检查脚本要求当前版本的更新说明存在，因此修改版本号与说明应一起提交。
4. commit、push 到 main。通过 `gh run list --workflow ci.yml` 找到**发布提交 SHA 对应**的任务，并用 `gh run watch <run-id> --exit-status` 等待成功。不能用较早提交的绿色 CI 代替本次结果。
5. 在该提交上创建 annotated Tag 并推送，例如 `git tag -a vX.Y.Z -m 'ScaleMate X.Y.Z'`、`git push origin vX.Y.Z`。推送前用 `python3 scripts/check_release.py --tag vX.Y.Z` 检查匹配。
6. 用 `gh run list --workflow release.yml` 找到对应 Tag 的 Signed Android Release，并等待成功。该流程重新运行测试与 Lint，构建固定签名 APK，验证包名、版本、版本码、非调试属性与固定证书，再创建 Release；缺少更新说明会失败，不再回退到旧版通用文案。
7. 查看 `gh release view vX.Y.Z`，确认更新说明正确、非草稿、prerelease 标记与通道一致，附件齐全：`ScaleMate.apk`、`SHA256SUMS`、`signing-certificate.txt`、`update.json`、`update.json.sig`、`releases.json`、`releases.json.sig`。预览版不能占用 Latest。
8. **下载实际 Release 附件重新核验**，不能只检查本地构建文件。示例中的目录和版本须替换为本次发布值：

```sh
gh release download vX.Y.Z --dir /tmp/scalemate-vX.Y.Z
(cd /tmp/scalemate-vX.Y.Z && sha256sum -c SHA256SUMS)
python3 scripts/check_release.py --tag vX.Y.Z \
  --apk /tmp/scalemate-vX.Y.Z/ScaleMate.apk \
  --build-tools "$ANDROID_HOME/build-tools/36.0.0"
```

核验时将 JDK 17 的 `bin` 放入 PATH，`apksigner` 需要通过 PATH 找到 Java。检查源码必须对应发布 Tag；不要在已切到下个版本的源码上核对旧 APK。最后确认最新版本下载入口和 Release 附件可用，再向用户提供下载链接与验证结果。

### 更新器元数据与代理复验

`update.json.sig` 是对清单原始字节的 RSA SHA-256 签名（Base64），公钥固定在客户端；不能重新格式化 JSON 后再验签。更新说明的前五个列表项生成变化摘要，预览版生成非空已知问题说明；发布前检查其内容是否具体符合本版。

下载后的 APK 校验之外，还要对实际下载的 `update.json`／签名验签并核对大小、摘要与当前发布字段。仓库外本地签名配置可安全导出公开验证材料：

```sh
python3 scripts/update_signing.py verify \
  --input /tmp/scalemate-vX.Y.Z/update.json \
  --signature /tmp/scalemate-vX.Y.Z/update.json.sig \
  --public-key /path/to/release-public.pem
python3 scripts/update_manifest.py verify --tag vX.Y.Z \
  --manifest /tmp/scalemate-vX.Y.Z/update.json \
  --apk /tmp/scalemate-vX.Y.Z/ScaleMate.apk
python3 scripts/check_update_sources.py --tag vX.Y.Z \
  --sha256sums /tmp/scalemate-vX.Y.Z/SHA256SUMS \
  --jobs 2 --timeout 180 --output /tmp/scalemate-source-report.json
```

元数据校验必须在对应 Tag 的源码上执行。公开验证公钥来自固定证书，不从第三方代理临时下载一个未经核对的新公钥。CI 在恢复 keystore 后导出公钥，并校验与 APK 内置公钥一致，再验签；签名用的私钥在步骤退出时删除。

代理仅转发 GitHub 文件，API 和文件支持不相同。内置官方与五条代理，每次发布复测附件；单线不可用时记录失败与网络环境，不能把一次测速当长期承诺。`ghfast.top`、`ghproxy.net` 曾明显较慢，应作为末尾备用。`gh-proxy.org` 首页跳转 `gh-proxy.com`，不能宣称两个域名是独立服务。

第一个包含更新器的版本仍需用户手动安装一次。已发布 `v0.2.1` 没有签名更新清单；不向旧 Release 补写附件来冒充当时就有更新协议。首次发布更新器后，必须实际验证更旧版本发现新版本、通过至少一条代理下载、Android 授权／安装取消重试、覆盖升级和数据保留。ADB 安装成功不能代替这条端到端流程。

### 失败处理与自动化边界

- 主分支 CI 负责元数据、检查器反例、翻译、JVM 测试、Lint 与 Debug 构建；不代替实机、真实 AI 和 Health Connect 验收。
- 发布流程自动校验 Tag／源码版本一致、更新说明非空、正式包名、APK 版本／版本码、非调试属性和固定发布签名。完整 Tag 历史用于自动校验两个通道的全局版本码递增；浅克隆、已知历史 Tag 缺失或元数据错误时停止，不能跳过后当作完整通过；说明真实性、同提交 CI 与下载后复验仍由执行者负责。当前 Tag 在比较时排除，不能拿自己和自己比较。
- CI 失败先修复并重新验收，不绕过门禁。尚未创建 Release 的临时网络故障可在确认同一源码安全后重跑任务；若 Release 已创建，先检查附件完整性和日志，不盲目重跑创建步骤。
- 已公开的 Tag 不移动、不删除重打；发布内容有误时说明问题并发布新版本。不要自动卸载手机 App 来“验证升级”，固定签名相同也不等于数据迁移已验证。

## 旧 debug 版

历史 debug 版与固定签名 release 版签名不同，不能直接覆盖安装。不要为解决签名冲突卸载仍有数据的手机 App。卸载会删除本地数据；需要先安排数据保留或迁移，再切换正式签名版。未来同签名的 release 版本可正常覆盖升级。

官方参考：[Android 应用签名](https://developer.android.com/studio/publish/app-signing)、[GitHub Secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)。
