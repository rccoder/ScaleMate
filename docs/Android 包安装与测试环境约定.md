# Android 包安装与测试环境约定

> 为后续 Agent 保留包名、签名、图标、数据隔离和清理决策，避免不了解历史时重复安装工具。本文是长期约定；当轮证据写在 docs/testing，不保存数据库、原始记录、密钥或私人图片。

## 先确认再安装

日常使用只需要一个称伴。正式版和公开预览版共用 `app.scalemate` 和固定发布签名，版本变化应覆盖原包；预览版不是独立开发版，也不能通过重新生成包名或签名解决安装冲突。

2026-10-18 用户确认：手机保留**正式称伴和饮食开发版**，升级验收结束删除原型及三个测试工具。后续 Agent 应先执行 `adb devices -l`、`pm list packages` 核对实际状态，再决定复用哪些包；本文历史清单不代表手机永远如此。

## 包名与角色

| 包名 | 用途／历史 | 数据与默认处理 |
| --- | --- | --- |
| `app.scalemate` | 用户日常称伴；固定签名从早期 release 延续，正式／预览共用 | 保护已有餐食、体重、设备、草稿、AI 服务与设置；只能正常覆盖升级 |
| `app.scalemate.fooddev` | `-PfoodDev` 的独立饮食开发版，用于隔离调试 | 有独立数据库、草稿与密钥；用户要求保留，不能擅自卸载或清数据；不是公开预览通道 |
| `app.scalemate.prototype` | 早期 AI 功能模拟原型，使用 prototype 构建类型 | 模拟能力不能当真实功能；本轮用户要求清理，后续仅有明确原型任务才安装 |
| `app.scalemate.test` | 固定仪器测试包，显示 ScaleMate Tests；每次构建的目标包和签名可能不同 | 复用同一个包名；测试结束卸载，目标 App 的业务数据不随测试包卸载而删除 |
| `app.scalemate.testing` | 历史测试应用，手机上曾为 0.1.0；非当前标准仪器测试包 | 不再创建或沿用此额外包名，本轮用户确认删除 |
| `app.scalemate.nutritionprobe` | 早期独立营养／健康权限探测工具 | 非日常称伴，不再为普通回归重复安装；本轮用户确认删除 |
| `local.scalemate.design` | 独立 design-prototype 工程的模拟视觉稿 | 不是业务 App；当前手机清单未发现，未安装时不为了截图新装 |

历史名称只能帮助识别，不能代替核对当前 APK 包名、版本、目标包和签名。其他未知包不在清理授权内；不要按模糊关键字批量卸载。

### 2026-10-18 收尾状态

本轮已清理上述原型及三个测试工具，实际复核仅保留 `app.scalemate`（公开正式 `0.3.0 / code 7`，绿色）和 `app.scalemate.fooddev`（独立开发 `0.3.0 / code 7`，橙色）。后者是保留原数据的同包同签名覆盖安装，不能因此将其当作正式数据的副本。正式／预览两次应用内升级及私有摘要验证、工具卸载结果见 [双通道发布验收](testing/应用更新双通道发布与升级验收-2026-10-18.md)。下一轮先核对实机，不根据旧清单重新安装已经清理的工具。

## 图标约定

- 正式／公开预览：绿色，使用 `@drawable/ic_scale`。两者共用包名，正常升级不会在桌面留下两个图标。
- Debug 构建、独立开发版、仪器测试包、Mock 原型与视觉稿：橙色，沿用同一秤形图案，使用 `@drawable/ic_scale_test`。名称仍明确标注“开发版”“Tests”或“原型”，不能只靠颜色区分。
- `app/build.gradle.kts` 根据 `foodDev`、debug 和 prototype 构建类型设置 `appIcon` placeholder；正式 release 默认为绿色。仪器测试有自己的橙色资源和 Manifest 图标，独立视觉稿也使用橙色。
- 不为颜色另建一个应用包，也不修改签名。校验时仍以包名、固定证书、版本码和非调试属性为准。

## 安装与收尾

1. 默认复用既有正式包和饮食开发包；普通 Debug 与正式版同包名但签名不同，不能通过卸载正式版来安装 Debug。
2. 安装仪器测试前核对 instrumentation 的 `targetPackage`。隔离测试目标应为 fooddev；对实际正式数据做只读升级对比时，目标必须为正式包，测试 APK 用同一固定发布证书签名，显式开启对应测试。
3. 系统拒绝 ADB 安装时先看实际错误和安装提示，不循环重试旧命令，不关闭系统安全机制。必要时通过正常系统安装页面安装测试工具，说明用途，结束清理临时 APK。
4. 清理工具时只卸载已确认的测试／原型包；不清除正式或开发包数据，不删除 Health Connect 历史记录。对系统安装权限做过临时变更时记录原值并恢复。
5. 测试 APK、私有摘要基线和夹具留在仓库外或应用私有目录，验证结束删除。截图只记录实际场景，避免把私人桌面、应用列表、健康记录或凭据归档。
6. 完成后记录实际保留包名和清理结果，让下一轮能从文档与实机两边核对。不要写成“测试版都可随便删”：饮食开发版可能包含用户数据。
7. 关键证据及时归档至对应 `docs/testing/` 与 `design/`，不能只留在重启会清空的临时目录；仓库外临时辅助脚本不是项目既有能力。恢复工作时先读最近验收记录，再检查手机与实际工具路径，避免因临时文件丢失重新安装应用。
