# 季度健康数据同步性能验收

- 日期：2026-10-26（Asia/Shanghai）；分支 `codex/health-ai-analysis`，修复基线 `672de49`。
- 构建：`-PfoodDev`，`app.scalemate.fooddev`，`0.3.3 / code 13`，橙色测试版；没有发布版本。
- 环境：本机 API 36 Google APIs 模拟器。手机检查包名／原签名、覆盖安装和业务数据保留，未测量手机同步速度。

## 结论与复现

用户感觉“仍在同步全量”有实际原因：超过一页时，下一页请求同时指定 `setAscending(true)` 与 `setPageToken(...)`，Android 原生 Builder 直接抛 `IllegalStateException`。失败类型不能提交完整缓存与游标，因此下次刷新、范围切换和重启又重读历史。旧的稀疏样例没有触发第二页，之前的性能结论不能覆盖季度密集数据。

按用户要求，在既有 `app.scalemate.healthseed` 来源中生成 2026-07-26 至 2026-10-25 的 92 天数据：50,186 条原生记录、132,480 个心率点。包括 5 分钟步数、15 分钟距离与活动热量、每分钟心率、每夜 HRV 与睡眠阶段、每日饮食和体重、隔日跑步。另保留来源原有的 208 条合成记录。样例与可重复命令见 [季度夹具](fixtures/health-quarter/README.md)。

授权模拟器当前 55 类读取和更早历史权限，9 类有数据，路线与医疗等其余类别为空。不是 55 类真实数据的完整性评测。测试运行真实平台和完整 `HealthViewModel`、同步、SQLite、指标、临时明细通路，使用独立 UUID 数据库，保留业务库。

基线的首次同步有 29 次步数分页构建异常，步数覆盖为 `partial`，仅落库 24,199 行；无变化刷新仍约 16 秒。未观测到限流异常，不能把平台配额作为本轮已证实的慢速原因。手机只读检查也发现步数、距离和心率缺少成功同步状态；未导出手机健康数值或游标。

## 修复

1. 第一页指定升序，后续页只设置平台分页令牌；原生 Builder 回归捕捉旧写法的异常。
2. 普通 Record 首次导入直接连续分页，不再按三天重叠扫描、发现最早记录后重复读取，或为中间分类结果写入并重新解析 JSONL；仍先捕获变更令牌，防止导入期间的变更遗漏。
3. 日汇总使用最多 90 个等时长本地日的批量原生聚合；首尾不完整日和夏令时的 23／25 小时日分组处理，增量只重算受到修改、移动或删除影响的日期。保留最多三类并发和每类事务。
4. 路线／医疗尚未使用普通变更令牌，成功读取后的缓存每 15 分钟重新核对；新授权、权限／时区或覆盖范围变化仍立即读取。这是有明确时效的本地快照，不宣称这些类别具有实时增量流。
5. 只有变更接口明确报告无效令牌才转为该类型全量恢复。临时平台、聚合或存储失败保留原记录与游标，供下次重试。
6. 无变化、同日、同范围、无失败且明细未过期时复用指标与明细；缓存版本与数据修改在同一事务中提交，快照必须匹配该版本。取消发生在提交后、页面更新前时，下次重建本地结果；旧缓存首次补建版本后即可复用，不重扫平台。
7. 需要新明细时直接流式复制已持久化 JSON，避免重新编码每个心率点；缓存来源名称和反射 getter，优化 SHA-256 十六进制转换，保持原记录 ID 与隐私字段排除规则。

未改变饮食识别 Prompt，未开启健康 AI、后台定时同步或更改今日／近期的信息结构。

## 测量

耗时从 ViewModel 操作开始，到 `busy=false`，包括同步、落库、指标和明细保存；采用约 50 ms 轮询，不代表亚毫秒精度。`after-restart` 是销毁并重建 ViewModel、重开同一数据库，证明持久化游标和快照复用；不是完整 Android 进程冷启动时间。以下是单机合成样例结果，不能当作手机或所有历史长度的速度承诺。

| 场景 | 修复前 ms | 最终修复后 ms |
| --- | ---: | ---: |
| 首次全量 | 33514 | 11844 |
| 无变化刷新一 | 16894 | 101 |
| 无变化刷新二 | 16543 | 101 |
| 查看 90 天 | 21217 | 8156 |
| 切回 7 天 | 16485 | 1913 |
| 重建 ViewModel 后刷新 | 16332 | 102 |
| 真实稀疏变更 | 未测 | 2124 |
| 变更后无变化刷新 | 未测 | 101 |

最终首次缓存 50,815 行，包含 50,394 条原始记录及平台聚合；季度样例和旧样例均已读入。稀疏变更后为 50,816 行，差异来自新增今日饮食、删除一条距离和对应日汇总变化。

Reader 观测的首次操作尝试从 912 次降到 159 次，其中普通分页从 481 次降到 90 次，聚合从 377 次降到 15 次。这里的计数包括 Builder 构建尝试，医疗读取按一个分类操作计数，不等于 Binder RPC 总数；可选路线授权查询由 ViewModel 自己的 Reader 执行，未计入测试注入 Reader 的分类计数，但包含在总耗时内。

无变化和重启后的注入 Reader 只有 42 类变更查询，没有全量、日聚合或医疗重扫；实际发生稀疏变更时只有 5 次受影响日聚合。范围切换没有调用平台全量或变更接口，也未改变最近读取时间。首次切到 90 天仍需解析、计算约 35 MB 的本地明细，约需 8 秒，是本轮保留的性能限制，不能描述为瞬时切换。

每次运行只读取合成统计、操作计数、耗时和文件大小作为报告，不归档原始明细、平台 ID 或变更令牌。可选观察器默认关闭，生产路径没有新增健康数据日志。

基线模式的 JUnit OK 只说明采集完成，报告中步数 `partial` 和异常仍是失败，不能当作通过。初步修复已经没有全量重扫，但无变化仍约 2.5 秒，进一步定位为重复解析、计算与写出明细，随后加入有版本校验的复用。首次设备复跑中，旧造数 Activity 被复用，变更动作没有执行，验证等待 30 秒超时；修正为变更前明确停止固定造数工具，再完整复跑通过，保留 [失败日志](2026-10-26-02-quarter-evidence/revision-first-attempt-instrumentation.txt)。

造数搭建期间遇到过工具覆盖安装后写权限被异步重置、结果 JSON 尚未写完整的问题；脚本现在核对权限连续稳定，并容忍读取中的空／不完整 JSON 后再重试。重跑再次复现过写权限被撤销，修正稳定检查后同一季度重新生成成功；这些属于模拟器夹具准备失败，未计作业务通过。脚本的非模拟器保护也已实际验证，拒绝后没有操作手机。

## 手机与清理

手机最终覆盖原橙色 `app.scalemate.fooddev`；先核对包名、版本及与原包相同的 debug 证书。安装前后仅在内存中读取数据库，比较设备、体重、餐食、模板、食物库、服务、饮食设置七表和已有偏好摘要，全部保留；临时摘要随后删除，仓库只保存布尔结果。手机当时息屏，未解锁、操作私人界面、安装仪器包或写入合成健康数据；用户打开后才会实际执行其数据的修复同步。

模拟器造数结束后仅删除 `quarter-20261026-` 前缀的本轮记录，保留旧合成样例与原 App；隔离数据库和快照由测试清理，临时仪器包在本轮结束移除。没有卸载业务 App、清空用户数据或更改公开包。

证据索引见 [证据目录](2026-10-26-02-quarter-evidence/README.md)。没有执行真实饮食 AI 回归、实秤或手机健康读取性能验收，这些不属于本轮已通过范围。
