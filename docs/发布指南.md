# 签名与 GitHub 发布

## 固定发布签名

发布密钥只生成一次，后续 APK 持续使用同一密钥签名。当前本地文件位于仓库外：

- `~/.local/share/scalemate-signing/scalemate-release.jks`：私钥库。
- `~/.local/share/scalemate-signing/credentials.json`：密钥库密码、密钥密码与别名。

目录权限 0700，文件权限 0600。请将这两个文件备份到加密存储或密码管理器；不要放进 Git 仓库，也不要在聊天或 CI 日志里输出内容。GitHub Secrets 是发布用副本，不代替自己的备份。

本地构建：准备 JDK 17 与 Android SDK 后运行 `python3 scripts/signing.py build`。密钥信息通过环境变量传给 Gradle，不写入项目配置。缺少完整签名配置时，release 打包会失败，避免发布未签名 APK。

## GitHub Secrets

完成 `gh auth login` 后，运行：

```sh
python3 scripts/signing.py upload-secrets
```

脚本通过标准输入设置以下仓库 Actions Secrets，不在命令参数或输出里包含秘密：

- `ANDROID_KEYSTORE_BASE64`
- `ANDROID_KEYSTORE_PASSWORD`
- `ANDROID_KEY_ALIAS`
- `ANDROID_KEY_PASSWORD`

设置位置：仓库 Settings → Secrets and variables → Actions。Base64 只是二进制编码，保密由 Secrets 提供。公众看不到；能修改并执行发布工作流的人可能获取秘密，因此发布工作流的修改权限也应由可信维护者掌握。

## CI 与发布

`.github/workflows/ci.yml` 在 main 提交、PR 或手动触发时检查翻译、运行 JVM 单元测试、Android Lint 并构建 debug APK，不读取签名密钥。手机仪器测试仍须实机运行。

`.github/workflows/release.yml` 在推送 `vX.Y.Z` 标签时检查版本号、测试与 Lint，再读取 Secrets 构建签名 release APK。密钥只在签名步骤恢复到 runner 临时目录，退出步骤时删除；签名任务不写入 Gradle 缓存。验证 APK 签名与 `gradle/release-certificate.sha256` 中的固定公开证书指纹一致，并确认非调试属性后，上传 APK、SHA-256 校验文件及公开签名证书信息到 GitHub Releases。

## 每次发布的标准流程

版本号使用 `X.Y.Z`。根据改动决定版本：修复递增补丁号，新增完整能力可递增次版本；`versionCode` 必须大于上一正式版。不要照抄历史文档中的版本号。

1. 完成相关功能验收与截图，按 [测试与验收指南](测试与验收指南.md) 记录结果和限制。检查工作区与待提交文件，不包含私有健康数据、密钥或测试安装包。
2. 更新 `app/build.gradle.kts` 中的 `versionName`、`versionCode`，添加非空 `docs/releases/vX.Y.Z.md`。更新说明覆盖用户能体验到的变化、安装升级限制、权限或费用边界；不把规划写成已实现。同步修正 README 中过时的版本提示。
3. 本地运行 `python3 scripts/check_release.py` 和 `python3 -m unittest discover -s scripts -p 'test_*.py'`；正常执行翻译、JVM 测试、Lint 与构建。检查脚本要求当前版本的更新说明存在，因此修改版本号与说明应一起提交。
4. commit、push 到 main。通过 `gh run list --workflow ci.yml` 找到**发布提交 SHA 对应**的任务，并用 `gh run watch <run-id> --exit-status` 等待成功。不能用较早提交的绿色 CI 代替本次结果。
5. 在该提交上创建 annotated Tag 并推送，例如 `git tag -a vX.Y.Z -m 'ScaleMate X.Y.Z'`、`git push origin vX.Y.Z`。推送前用 `python3 scripts/check_release.py --tag vX.Y.Z` 检查匹配。
6. 用 `gh run list --workflow release.yml` 找到对应 Tag 的 Signed Android Release，并等待成功。该流程重新运行测试与 Lint，构建固定签名 APK，验证包名、版本、版本码、非调试属性与固定证书，再创建 Release；缺少更新说明会失败，不再回退到旧版通用文案。
7. 查看 `gh release view vX.Y.Z`，确认更新说明正确、非草稿且附件齐全：`ScaleMate.apk`、`SHA256SUMS`、`signing-certificate.txt`。
8. **下载实际 Release 附件重新核验**，不能只检查本地构建文件。示例中的目录和版本须替换为本次发布值：

```sh
gh release download vX.Y.Z --dir /tmp/scalemate-vX.Y.Z
(cd /tmp/scalemate-vX.Y.Z && sha256sum -c SHA256SUMS)
python3 scripts/check_release.py --tag vX.Y.Z \
  --apk /tmp/scalemate-vX.Y.Z/ScaleMate.apk \
  --build-tools "$ANDROID_HOME/build-tools/36.0.0"
```

核验时将 JDK 17 的 `bin` 放入 PATH，`apksigner` 需要通过 PATH 找到 Java。检查源码必须对应发布 Tag；不要在已切到下个版本的源码上核对旧 APK。最后确认最新版本下载入口和 Release 附件可用，再向用户提供下载链接与验证结果。

### 失败处理与自动化边界

- 主分支 CI 负责元数据、检查器反例、翻译、JVM 测试、Lint 与 Debug 构建；不代替实机、真实 AI 和 Health Connect 验收。
- 发布流程自动校验 Tag／源码版本一致、更新说明非空、正式包名、APK 版本／版本码、非调试属性和固定发布签名。版本码相对上一版的递增、说明真实性、同提交 CI 与下载后复验仍由执行者负责。
- CI 失败先修复并重新验收，不绕过门禁。尚未创建 Release 的临时网络故障可在确认同一源码安全后重跑任务；若 Release 已创建，先检查附件完整性和日志，不盲目重跑创建步骤。
- 已公开的 Tag 不移动、不删除重打；发布内容有误时说明问题并发布新版本。不要自动卸载手机 App 来“验证升级”，固定签名相同也不等于数据迁移已验证。

## 旧 debug 版

当前手机上的 debug 版与新的 release 版签名不同，不能直接覆盖安装。本次发布不会卸载手机 App 或清除已有记录。卸载会删除本地数据；需要先安排数据保留或迁移，再切换正式签名版。未来同签名的 release 版本可正常覆盖升级。

官方参考：[Android 应用签名](https://developer.android.com/studio/publish/app-signing)、[GitHub Secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)。
