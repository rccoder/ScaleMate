## 一、产品方向与已确认决策

称伴从“体重秤到健康平台的桥梁”扩展为“记录摄入、连接身体数据、帮助采取行动”的个人健康工具。现有上秤记录继续是可独立使用的核心能力。

| 项目 | 决策 | 状态 |
| --- | --- | --- |
| 产品载体 | 在当前 ScaleMate 项目和正式 App 内实现，不发布两个独立 App | 用户确认 |
| 文档组织 | 食物 AI 记录、健康 AI 分析各一份独立 PRD；本篇是总述 | 用户确认 |
| 默认体验 | 记录首页为中心；秤引导在称重 Tab；功能阻碍按需引导并提供降级路径 | 用户后续确认 |
| 食物方向 | 拍照识别热量、蛋白质等，保存并写入 Health Connect，供 Google Fit 等应用读取 | 用户确认 |
| 分析方向 | 直接从 Health Connect 读取运动、睡眠、心率等，提供个性化健康建议 | 用户确认 |
| 首版分析体验 | 包含日常对话和主动提醒，不能只交付静态周报 | 用户确认 |
| 价值主张 | “无会员也能有教练”：无需购买称伴会员即可使用核心 AI 能力 | 用户确认的产品方向 |
| AI 接入 | 首版用户自带 API Key；可保存多个服务，声明模型是否支持图片，并按能力设置默认服务或临时选择 | 用户确认 |
| 开放性 | 用户可自由选择模型服务；健康数据 JSON 和配套问询 Prompt 可导出，供外部 AI 使用，无须先配置内置 AI | 用户确认 |
| 食物辅助信息 | 拍照后多选预设标签并追加自定义描述；支持复用已记录食物和逐项修改营养结果 | 用户确认 |
| 健康预设问询 | 提供常见问题入口，支持编辑后提问 | 用户确认 |
| 操作系统与设计 | 沿用 Android 14+、Kotlin、Compose、Material 3、中英文与主题设置 | 基于现状的产品建议 |
| 功能交互细节 | 本文及两份 PRD 中未标为用户确认的具体交互、阈值和指标，均是可评审方案 | 草案约定 |

称伴保持开放：记录、整理、分析入口与用户所选模型分离；用户可以在 App 内使用自己的 AI 服务，也可以导出后在其他 AI 中分析。不将“无会员”宣传为无限免费调用，第三方服务费用由用户承担并明确说明，不暗设强制会员入口或导出门槛。

## 二、当前项目与实测基础

### 2.1 规划时的项目基线

本节保留规划前的 0.1.1 基线，用于解释接入位置；后续饮食实现、数据库升级、记录首页和实机验证状态以 [饮食功能实现与验收](testing/饮食功能实现与验收.md) 为准。

规划时源码 `app/build.gradle.kts`：`versionName = 0.1.1`、`versionCode = 3`；最低 Android 14，编译／目标 SDK 36。主模块是 `app/`；早期称重视觉稿已移除，[健康 AI 设计](../design/ai-prototype/README.md)按用户要求保留用于未来开发，历史见 [项目演进](项目演进.md)。

| 现有实现 | 当前职责 | 扩展方向 |
| --- | --- | --- |
| `ScaleMateApp.kt` | 称重、体重记录、设置以及首次引导 | 增加饮食与健康入口，复用外观和语言 |
| `ScaleViewModel.kt` | BLE 会话、体重状态、持久化和前台同步 | 继续负责称重；新功能使用独立 ViewModel，避免无限扩充 `AppState` |
| `data/Store.kt` | SQLiteOpenHelper，数据库版本 1，`scales`、`measurements` | 增量迁移，新业务独立表，不重建数据库 |
| `platform/HealthOutput.kt` | 原生 HealthConnectManager，写入／删除 WeightRecord | 保留体重能力；新增营养写入与健康读取模块 |
| `MainActivity.kt` | 单项体重授权、附近设备授权、生命周期 | 按功能请求多项健康权限；按需新增相机、通知和后台读取 |
| `PrivacyActivity.kt` | 现有隐私说明 | 更新照片处理、模型服务、健康摘要发送与本地保留说明 |

上述基线当时没有 AI 网络客户端；现在饮食识别已实现，健康 AI 分析、后台健康读取调度和提醒仍未实现。不要用规划时的基线推断当前能力。

0.1.1 的“上秤自动记录”仍以已有前台运行和保存方式为准；新增后台健康提醒不等于实现后台 BLE 自动称重。

### 2.2 已验证与未验证

- 独立测试工具已写入一条包含热量、蛋白质、碳水和脂肪的 NutritionRecord，用户确认目标 Google 应用能够读取。正式 `app.scalemate` 的接入、更新、删除和不同目标版本仍需验收。
- 已直接调用 Health Connect 读取到睡眠、心率、HRV、运动、步数等。详细样本包含睡眠阶段和心率采样，可支撑本地统计和结构化分析。
- 读取数据来自手机上实际共享的数据，不是 Google Fit 云端全量备份。历史权限不负责把来源 App 未共享的记录补过来。
- 此条记录规划时的未验证范围；后续饮食识别与本人摄入合同已实现并验收，模型估算不等于营养准确率验证。主动提醒仍属规划。
- 不把真实个人健康明细、API Key、手机标识或原始导出提交仓库；验收数据使用合成样本。

## 三、统一体验与项目接入

### 3.1 信息架构建议

用户已确认新的中心是“记录并按需同步”，默认进入 **记录** 首页。完整规划的五个入口为：**记录、饮食、称重、健康、设置**。本轮先开放记录、饮食、称重、设置，健康分析完成后再开放健康入口，不放不可用的空壳页。

- 记录：首页显示今日饮食与体重、按时间排列的记录、待同步数量和快捷记录动作；全部历史从首页进入并按类型查看。这里只汇总称伴已有记录，不冒充 Health Connect 全量健康数据。
- 饮食：今日已记录摄入与餐次；进入一餐后通过拍照、多图相册、添加食物组合记录。常吃与历史合并为食物库，常吃只是标记；AI 服务只在使用处按需提示。
- 称重：首次未绑定时引导添加、试称核对和保存方式；完成后使用现有自动接收流程。设置只保留设备管理的备用入口。
- 健康：后续接入数据分析、对话和提醒；本轮不扩展其正式业务逻辑。
- 设置：外观、语言、设备、AI 服务与分类同步授权。

首次进入只介绍“记录在本机、可同步到 Health Connect、AI 自选服务”，点击“开始记录”进入记录首页。不强制先安装 Google Fit、添加秤、授权蓝牙或填写 Key。已有用户不重新走欢迎流程，秤和保存偏好照常保留。

**按需引导是首版验收内容：**

| 阻碍 | 出现位置 | 下一步与降级 |
| --- | --- | --- |
| 无视觉 AI／仅有文本模型 | 用户尝试图片识别 | 配置图片服务、手动录入或常吃食物；保留草稿 |
| 未绑定秤 | 称重 Tab | 添加秤、试称核对、选择保存方式；不阻断其他 Tab |
| 缺营养／体重写入权限 | 首次保存对应记录后、记录详情和设置 | 先保存本地，按类别授权，或稍后继续；无需重新记录 |
| Health Connect 不可用 | 同步状态／设置 | 显示本地保留，打开系统健康连接设置，服务恢复后重试 |
| 写入失败／删除失败 | 对应记录详情 | 解释当前状态并提供重试，保留稳定 ID 与待删除任务 |

不要用一个“已连接”代表全部类型已授权，也不要把“已写入 Health Connect”写成“Google Fit 已显示”。

### 3.2 共用能力与边界

| 共用能力 | 要求 |
| --- | --- |
| AI 接口层 | 统一凭据、超时、取消、错误映射、结构化结果校验和服务余额／限流等错误状态；区分用户声明的视觉能力与实际校验结果 |
| Health Connect | 权限按类别分开，不再使用单个 `healthAllowed` 代表全部健康能力；读取状态区分未授权、空数据、过期和失败 |
| 本地存储 | 分业务 Repository 与表；事务保存记录和待同步任务；升级保留秤、记录、设置 |
| 个性化上下文 | 目标与用户自报背景属于健康分析规划；当前没有饮食完整性标记，不恢复已撤回字段，饮食只表达已记录摄入 |
| 跨功能分析 | 饮食功能未开启时，健康功能仍可分析睡眠／活动；不以记录的餐数推断实际吃了多少 |
| 网络与隐私 | 现有称重与本地记餐可离线；在线 AI 需要网络。开启时明确发送什么、发送给谁，服务切换后重新说明接收方 |

当前原生 HealthConnectManager 能满足已验证路径，首版不为了新功能强制整体替换 SDK、数据库或 UI 框架。

### 3.3 数据与模型约定

本地负责汇总、单位与格式校验；饮食 AI 直接返回本人摄入，应用不再执行人数或食用比例换算。健康分析中的统计与提醒仍属规划，不能用此约定改写当前饮食合同。模型不直接执行健康数据写入、删除、权限变更或通知发送。

食物照片、健康摘要进入不同任务；食物识别请求不附加健康历史。健康对话默认发送最小必要摘要，不发送全量心率原始点、来源包名和平台记录 ID。

用户可预览发送范围；对已选择的服务及已同意用途不逐次重复弹确认。新增数据类别、用途或服务接收方时再确认。用户拒绝网络 AI 后，称重、手动记餐、本地趋势仍可使用。

## 四、AI 服务配置与开放使用

### 4.1 首版决定

**D-AI-01 已关闭：首版采用用户自带 API Key。** 官方免费额度不属于首版范围，不再以商业方案未定阻塞两个功能。首版不要求称伴账号，不内置官方共享 Key。

设置页“AI 服务”支持新增、编辑、删除多个配置。每项对应一个实际调用配置：显示名称、接口格式（OpenAI／Anthropic）、Base URL（远程 HTTPS 或用户配置的私有局域网 HTTP）、modelId、API Key 安全引用、“支持图片”勾选、连接状态、可选最近测试时间。同供应商不同模型可保存为不同配置，能力不能只绑定供应商名称。

用户已确认首版支持 **OpenAI 兼容（Chat Completions）与 Anthropic 兼容（Messages）** 两种接口格式，每个服务独立选择。适配包括路径、认证、图片消息和响应解析；具体服务兼容性以端到端验收为准，不声称所有提供 Key 的服务都兼容。模型名允许手动填写，模型列表发现失败不能阻止配置。扩展协议不改变用户已保存的数据与默认路由。

### 4.2 声明能力与验证

- 普通文本能力是健康对话和报告的基础；图片能力由用户勾选。“已勾选”不是已经测试通过。
- 提供用户触发的连接测试，默认只发合成文本；图片测试需用户主动选择合成测试图，不暗中上传照片或健康数据，并说明可能消耗服务商额度。
- 用户声明不支持图片时，食物拍照／相册 AI 识别不可用；保留手动录入、常吃食物和历史复用，不用纯文本模型猜照片内容。
- 已声明支持但实际拒绝图片时，保留草稿并标记当前服务图片调用失败；可选其他视觉服务或转手动，不自动删除能力声明。
- 模型返回内容仍需结构校验；“能连通”“能看图”“本任务结果有效”是不同状态，不把连接测试当质量保证。

### 4.3 按能力路由与当次选择

首版提供“食物图片识别”和“健康分析与对话”两个默认服务选择，同一服务可同时担任两个角色。饮食选择器只列出已声明支持图片的配置；健康选择器列出支持文本调用的配置。未设默认且只有一个合格配置时，可预选并清楚显示；多个时请用户选择，不能随机调用。

在拍照识别确认页、健康对话输入区、生成报告之前都能看到当前服务并切换。“仅本次”不改变默认；“设为此能力默认”需显式选择。请求开始后固定 serviceId、模型与配置版本，切换仅作用下一次请求；正在生成需先取消或等待。

不会因余额不足、超时或图片失败静默切到另一家服务。用户主动重试或切换，保留问题／草稿并说明新的接收方。已告知接收方和用途不逐条重复弹窗，但新增接收方必须在发送前完成说明。

删除默认服务时清空受影响路由并提示重选，不随机找替代；历史报告／餐食保留生成时的服务名称与模型版本，不依赖服务配置仍存在。新请求中止或固定快照规则应明确，不读取被修改后的凭据继续旧请求。

### 4.4 凭据与费用

Key 使用 Android Keystore 支持的凭据保护方案保存，不进入普通 SharedPreferences 明文、日志、备份、健康 JSON 或 Prompt。配置页默认遮挡 Key，允许替换和清除。所有自定义远程地址使用 HTTPS；按用户后续明确要求，额外允许主动配置的 RFC1918／回环 IPv4 字面量 HTTP 测试服务，并在配置及发送说明中标明局域网明文传输。其他 HTTP 地址拒绝，禁止跟随携带凭据的重定向。协议和最终 URL 拼接规则须在连接测试中校验。

费用由用户所选服务商决定，不承诺能准确读取余额或跨服务统一显示费用；可显示本次服务／模型、已知的用量，不编造价格。官方额度保留为未来选项，新增时另行评审账号、预算和隐私链路。

建议新增 `AiServiceProfile`（id、name、protocol、baseUrl、modelId、secretRef、supportsImages、configVersion）与 `AiCapabilityRoute`（capability、defaultServiceId）；配置版本不含密钥原文。`AiSettingsRepository` 与请求解析器供两个功能共享，升级迁移与现有 Store 统一安排。

### 4.5 开放导出

健康页提供“导出给其他 AI”，不要求 Key、联网或 AI 调用成功。用户选择范围后获得标准 JSON 和配套 Prompt，可下载、系统分享，也可只复制 Prompt。摘要是默认，原始明细可选；详见健康 PRD。文件具备 schemaVersion、单位、时间口径、来源和缺失说明，不以称伴专用会话 ID 作为理解前提。

后续更换模型或停用在线 AI，不影响本地记录、历史查看和导出。不把“开放”扩展为未经确认的开源许可或公开用户数据。

## 五、交付顺序与共同验收

### 5.1 交付切片

| 顺序 | 交付 | 说明 |
| --- | --- | --- |
| A | 数据库迁移、权限拆分、AI 服务抽象、功能入口 | 两份功能共用基础，先验证 0.1.1 升级数据保留 |
| B1 | 手动／AI 记餐、确认、营养写入与删除 | 食物 PRD 的完整可用切片 |
| B2 | 健康读取、质量分析、报告与日常对话 | 健康 PRD 的核心分析切片，不依赖 B1 才能使用 |
| C | 主动提醒、后台能力检测、触发／去重与权限降级 | 属于健康首版范围，不能整体推到“未来再做” |
| D | 两功能联合分析、AI 质量回归和正式包验收 | 按首版 BYOK 和能力路由完成端到端测试 |

以上是实现依赖顺序，不指定下一版版本号、发布日期或承诺工期。

### 5.2 共同验收

1. 从 0.1.1 原地升级：设备绑定、称重记录、自动保存方式、语言和主题全部保留。
2. 不启用 AI 的用户继续完成原有称重和 Health Connect 写入；无需申请图片、营养读取或通知权限。
3. 两个功能分别验收，任意一项未配置服务或被拒绝权限，不阻断另一项。
4. AI 取消、超时、限流和服务错误不损坏已保存记录；成功统计和同步结果能追踪到对应版本。
5. 所有新页面具备中英文、深色模式、大字体与读屏可用性。
6. 日志不包含 Key、照片、完整健康对话或原始健康记录；导出由用户触发并说明内容。
7. 多服务按能力路由、当次覆盖、删除默认服务和视觉能力不匹配均有明确结果；失败不会静默跨服务重发。
8. 无 Key 可导出可解析 JSON 和配套 Prompt，文件不含凭据；使用外部 AI 不要求先开通内置分析。
9. 正式包不得暴露 mock 写入或批量导出调试入口；旧独立探测工具已移除；原始探测结论只作历史依据，不能当成正式业务已接通。
