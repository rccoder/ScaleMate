# 照片变更后的再次分析与输出预算

- **日期**：2026-11-01（Asia/Shanghai）
- **基线**：`main` 工作区，尚未提交
- **性质**：再次分析边界审查、`max_tokens` 请求预算核对与本地自动化验收
- **未修改 Prompt**：因此没有重新执行 4 张真实 AI Prompt 基准

## 用户问题

1. 第一次分析后，如果稍后增删或替换照片再分析，旧结果会不会被误当成当前照片的基线？
2. 食物识别的 `max_tokens` 是多少，是称伴设置的还是 AI 提供方设置的，当前值是否合理？

## 再次分析决策

### 照片没有变化

只修改分食人数、标签或补充说明后再次分析：

- 上一次待确认结果作为基线，连同本次修改要求和原照片发送；
- 分析期间继续展示旧结果；
- 成功后用完整的新结果整体替换；
- 失败、取消或中断保留旧结果。

这是已有的“基于上次结果重新分析”路径，不能把旧结果当作新的照片证据。

### 照片发生增删或替换

照片集合一旦变化，旧分析就不再对应当前证据：

- 清空旧食物结果、整餐建议、Token／耗时和上一轮修改说明；
- 保留分食人数和标签，因为它们仍是当前餐食的上下文；
- 状态回到待分析，按当前照片从零开始；
- 不把旧结果作为 Prompt 基线，也不追加旧食物副本。

当前没有独立的“替换照片”按钮；实际交互是移除旧图后再添加新图，两条路径都经过 `FoodBatch.withChangedPhotos()`。首次添加照片时尚未产生分析，用户已经填写的说明不会被清空。

实现位置：

- `FoodModels.kt` 的 `FoodBatch.withChangedPhotos()`
- `FoodViewModel.removePhoto()` 与 `importPhotos()`
- 中英文“基于上次结果重新分析”说明文案

## `max_tokens` 现状

### 谁设置

食物识别由称伴在每次请求中主动设置，不是 AI 提供方的默认值：

```kotlin
internal const val FOOD_ANALYSIS_MAX_TOKENS = 4096
```

OpenAI 兼容请求发送 `max_tokens: 4096`；Anthropic 请求同样使用应用传入的 `max_tokens: 4096`。供应商仍可以在自己的模型上施加更小的实际上限、拒绝该字段或返回不同的结束原因，因此 4096 是**应用请求的输出预算上限**，不是供应商模型的全部能力。

### 当前是否合理

对当前食物结构化 JSON 请求，4096 是合理的保守预算：

- 2026-11-01 同一张用户照片的真实成功请求，服务返回输出 Token 约 695–773；
- 当前结果在约 6.8–7.5 秒完成，4096 约有 5 倍余量；
- 之前 DeepSeek 默认推理会把 512 Token 全部消耗在推理并返回 `length`；现在对 DeepSeek OpenAI 兼容服务发送 `reasoning_effort: none`，关闭这条慢路径；
- 盲目把预算提高到数万不会提升正常回答质量，反而可能扩大最坏情况下的等待、费用和截断前的处理量。

如果未来切换到不能关闭推理的模型，或者真实请求开始出现 `finish_reason=length`／`stop_reason=max_tokens`，才应根据该模型的 reasoning 计费规则和实测结果调整；不能把供应商宣传的 128k 输出能力直接当成每次请求预算。

### 多图会不会超

多图不会直接把照片数量加到 `max_tokens` 上。`max_tokens` 约束的是生成结果，照片、Prompt 和上次分析数据属于输入上下文；是否超限取决于服务商的上下文窗口和请求体限制。

称伴当前的客户端边界是：

- 每批最多 6 张照片；
- 每张照片最长边不超过 1024 px，JPEG 质量 70；
- 压缩后单张不超过 1.5 MB，合计不超过 8 MB；
- Base64 编码后请求体约为原始 JPEG 合计的 4/3，最大约 10.7 MB。

单张用户照片的真实请求记录为输入约 2,800 Token；6 张照片通常不会因为输出预算 4096 而直接失败，但输入 Token、请求体和供应商图片数量限制仍需按具体服务验证。多图如果包含很多独立菜品，输出 JSON 也会变长；当前 Prompt 限制最多 20 个食物，极端情况下 4096 仍可能偏紧，不能把“普通一餐通过”扩大成“任意 6 图都保证通过”。

## 边界

- 本轮没有重新调用真实 AI，不能把 Mock／固定响应或状态测试冒充真实模型再次分析质量。
- 没有修改 Prompt，因此未触发 4 张真实 AI Prompt 基准回归。
- 替换照片的实际产品交互是“移除后添加”，不是独立替换控件。
- 当前使用兼容性更广的 `max_tokens` 字段；如果未来适配要求 `max_completion_tokens` 的供应商，需要单独做协议分支和真实回归，不能只改字段名。
